# Architecture

nx2android turns a player's own Switch game files into an Android app. The player picks the game's folder, clicks **Port**, and gets an APK plus the game's data, which the tool can install on a connected device. Every game the tool supports is a **game profile**; everything all games share is the **core**.

```
gui/  (PySide6 desktop app)
  │  runs `python -m porter port … --progress json`, draws the JSON events
  ▼
porter/  (headless port pipeline, also a CLI)
  │  inputs → extract → rewrite → shaders → host → apk → data pack → [install]
  │  reuses nxnative/scripts/build_ipa_from_nsp.py's steps (imported, not copied)
  ▼
nxnative/  (our fork of seedds/nxnative + the Android port)
  ├─ dm/host, dm/gfx, dm/tools        core: Horizon host, NVN layer, rewriter, shader split   (shared with iOS)
  ├─ dm/android                       core: Android runtime (Vulkan backend, front end, build.py, mkapk.py)
  └─ dm/games/<title ID>/             profiles: game.tsv + shader tables (+ patches.py) + android.tsv
```

## Layers and their rules

| Layer | Where | Holds | Must not hold |
|---|---|---|---|
| **Core, shared** | `nxnative/dm/{host,gfx,tools,third_party}` | What every game and both platforms need. Android differences behind `DM_ANDROID` / `__APPLE__` / `DM_TARGET`. | Game-specific branches. |
| **Core, Android runtime** | `nxnative/dm/android/` | Vulkan replay backend (`gfx_vk_*`), the NativeActivity front end (on-screen gamepad, pause menu, settings, the save manager's export and import, text entry with an on-screen keyboard, haptics, shaking the device as shaking the controller, audio, performance hints), the NDK build (`build.py`), the APK writer (`apk/mkapk.py`), the Vulkan shader bundle (`tools/shader_vk.py`), the profile's Android header (`tools/android_profile.py`), the gamepad's layouts (`overlay_default.tsv`: tablet and phone) and its themes (`themes/`: a sprite pack per design, and `themes.tsv`, the table of which game wears which; `themes/README.md`). | Code that depends on a game: no title IDs, game names or per-game branches in code (comments may name the game a rule was found with, as upstream's do). A game that needs something different gets a profile key. |
| **Game profile** | `nxnative/dm/games/<title ID>/` | Data only: `game.tsv` (upstream keys), shader tables, `patches.py` (per-build rewriter cuts), and `android.tsv` (Android keys, below). | Code paths. |
| **Port pipeline** | `porter/` | The stages that turn game files into the APK and data pack; the toolchain check; the profile registry; installing over adb. Runs headless. | UI. |
| **GUI** | `gui/` | Screens over `porter`: setup check, game folder, profile status, options, progress, install. | Pipeline logic: everything it does, the CLI does too. |
| **Distribution** | `packaging/` | The player's bundle (`build_bundle.py`, PyInstaller): one executable that is the GUI and the Python the pipeline runs the engine's tools with (`nx2android.py`), the committed `nxnative/` beside it, the install guide (`INSTALL.md`). | Pipeline logic or toolchains. |
| **Dev tools** | `devtools/` | Scripts for bringing up a game on a connected device (pushing files, screen recording, soak tests, pass traces). The device comes from `devtools/device.json` or `NX2A_DEVICE`. | Anything the port needs. |

The game profile is compiled into the host (`game_profile.h` and `android_profile.h`, generated by `build.py`), as upstream does: porting a game builds its host with the player's NDK, which takes seconds.

## Game profiles on Android

A profile is offered for Android when it has an `android.tsv`; the profiles without one (52 of the 54 today, upstream's iOS games) show as "ios only": an experimental port can still try them. `android.tsv` holds, one `key<TAB>value` row each:

| Key | Meaning |
|---|---|
| `status` | `playable` (tested end to end on a device), `wip` (plays on a device, but parts are missing: README.md's Games table says which), `boots` (starts, not playable yet) or `experimental` |
| `tested` | `<version> <device>`: the version and device the status was checked on |
| `package` | The app's package name (default `org.nx2a.t<title ID in lowercase>`) |
| `orientation` | `landscape` (default) or `any` |
| `requires` | Device features the game needs, checked by the installer: `bcn` (BC texture compression) |
| `setting` | `<name>=<value>`: the pause menu's defaults on first launch (`overlay`, `rumble`, `docked`, `fps`: the frame rate counter in the top left corner, off by default; `opacity`: the gamepad's, 20 to 80 percent by 5, 60 by default), written to the data pack's `settings.txt`, where the app also keeps the player's own gamepad layout from the pause menu's layout editor (`ui=` rows) and its Snap to grid (`grid`, off by default) |
| `env` | `<KEY>=<VALUE>`: a host switch the game needs on Android, written to the data pack's `env.txt` |
| `overlay` | `<tablet\|phone> <control> <x> <y>`: moves one on-screen control of that layout (`dm/android/overlay_default.tsv`) to x, y as fractions of the window, compiled into `android_profile.h` |

Per-build knowledge stays where upstream keeps it: the rewriter's cuts in `patches.py` / `dm/tools/sdk_patches.py`, keyed by build ID.

Runtime GLSLC shaders can be captured while porting on an Apple Silicon Mac. The pipeline
rewrites a separate Apple-target copy of the modules, boots the silent, headless Mac host,
and checks the capture against the profile before splitting shaders. Other hosts can reuse
a complete capture beside the extraction; without one they stop with an explanation.
Merged NSP/XCI packages that contain both application and patch metadata are used for
both extraction roles, with NCAs selected by the corresponding content metadata.

## The port

`python -m porter port <game folder> -k <prod.keys>` (the GUI's **Port** button) runs these stages. The slow ones (extraction, rewrite, shader split, the translator build, the Vulkan shaders) keep their output with a key of their inputs and are skipped on the next run when the key is unchanged; the host build is incremental (`build.py`), and the APK and the data pack are made again each time (seconds).

| Stage | What | Output (in `<game folder>/<title ID>_build/`) |
|---|---|---|
| inputs | Find the base game, updates and DLC (NSP / XCI / NSZ / XCZ), match the profile, pick the version; check the game folder's drive has room (about twice the game files, NSZ / XCZ counted decompressed and once more for their NSP, less an earlier port's build folder) | |
| decompress | Only with NSZ / XCZ files that a stage below will read (a reused extraction reads none): each becomes an NSP (an XCZ: an NSP of its secure partition), its NCZs expanded and encrypted again with the keys their section tables carry, every NCA checked against its SHA-256 name (`porter/dumps.py`). Deleted once the DLC are extracted, or when the port fails | `tmp/dumps/` (temporary) |
| extract | `nx_extract` (built with the .NET SDK) | `extract/<version>/{ExeFS,RomFS}`, `aoc/` |
| 60 fps | Only with `--fps60` (below): the profile's own cap, or the build's FPSLocker-Warehouse config converted for the host | `android/fpslock/{fpslock.tsv,patches.py,<build ID>.yaml}` |
| rewrite | `patch_nso.py` with `DM_TARGET=android` | `android/patched_<version>/` |
| shaders | `shader_split.py` (the DLC's own shaders too, `aoc/` given as `DM_SPLIT_AOC`), then `shader_vk.py` (SPIR-V) with the translator built from the repository's source (`dm/gfx/tools/dmsh_xlate` over `dm/third_party/ryujinx`, once per player in their nx2android folder), plus the shaders captured on the device (below) | `shader/pkg`, `android/shaders.dmsv`, `android/captured_shaders/` |
| host | `dm/android/build.py --release` with the player's NDK (`--debug`: a development build, debug information and `DM_CTL`) | `android/host/libdmhost.so` (`android/host-debug/`) |
| apk | `dm/android/apk/mkapk.py`, signed with the player's own key, with the game's gamepad theme only (`dm/android/themes/themes.tsv`: its pack, else the ergo pack) as `assets/overlay/` | `<out>/<App>.apk` |
| data | The files the app reads from `/sdcard/Android/data/<package>/files` | `<out>/<App>-data/{mods,RomFS,aoc,shaders.dmsv,nintendo_ext.ttf,env.txt,settings.txt,nx2a-data.json}` (+ `fpslock.tsv` with `--fps60`); the button-icon font is made in `android/font/` |
| install | `adb install`, the profile's `requires` checked against the device, the data pack pushed (optional) | |

RomFS in the data pack is hard-linked to the extraction when the volume allows it, so it takes no extra space.

Android memory pools normally import an AHardwareBuffer for zero-copy GPU access.
`DM_VK_ZEROCOPY_MIN_KB=<n>` optionally routes whole NVN pools smaller than n KiB
through the existing copied-pool path, avoiding hardware-buffer allocation and remapping
for frequently recreated small pools. The default is 0 (unchanged zero-copy policy).
The threshold is based on the whole pool, so a small final chunk of a large pool stays zero-copy.
`DM_VK_ZEROCOPY_MAX_MB` and `DM_VK_NO_ZEROCOPY` keep their existing precedence.

The opt-in `DM_GPU_TURBO` switch is a device-global KGSL profiling override,
not an app-owned performance session. On Gen7 it pauses GPU/bus devfreq, blocks
GMU SLUMBER and requests the highest allowed power level; thermal/max bounds
still apply. Tests require independent restoration because process death need
not release the property. Keep it off by default; a production performance
request should have verified context/session ownership and lifecycle cleanup.

`porter port --gpu-perf` is an experimental opt-in that packages the context hook
and writes `DM_GPU_PERF=1`. It keeps the system Vulkan driver unless a custom
driver was separately requested. The optional loader observes the driver's own
KGSL context creation and requests an existing maximum performance level on
the same fd; no global power-control property is used. Default loading is
unchanged. `DM_GPU_PERF=2` is a diagnostic control: the same isolated stock
loader and hook, with context requests disabled. Compare 2 versus 1 before
attributing improvements to the request. Process-lifetime hook counters
distinguish interception, accepted flags and accepted property requests;
acceptance is not hardware activation. Context destruction clears its owned
constraint, while idle expiry and actual frequency remain governed by the
kernel. Device validation of interception, active performance and cleanup is
required before this option can become a tested recommendation.

`DM_VK_CPU_SMALL_UPLOADS` is a default-off bounded-copy experiment. Mode 2
only counts metadata eligibility and preserves the ordinary GPU submission;
mode 1 copies eligible data synchronously after all prior GPU work is complete.
It accepts only a single exact copy record with no event/fence operations,
a tiny copied CPU-uncached source and a zero-copy destination whose actual
Vulkan memory type is HOST_VISIBLE and HOST_COHERENT. In either diagnostic
mode, AHB imports prefer such a compatible type; mode 0 keeps the usual type
selection. Any intersecting pool alias, including a partial alias, rejects the
host path. Backend submission ownership covers inspection and copying; queue
ownership also excludes presentation work, with one idle wait per changed queue
epoch. Mode 1 maps the Vulkan allocation once and writes through its returned
persistent mapping. Missing memory properties or a mapping failure retains the
GPU path. Host-write preparation preserves dirty tracking; no GPU fence is
invented for a completed CPU copy. Per-copy AHardwareBuffer lock/unlock was
rejected after device measurement showed whole-allocation synchronization cost.
Android `DM_THREAD_WAIT_PROF=1` separately exposes bounded yield/back-off
summaries even without Mach power counters.

`DM_VK_LAZY_SMALL_POOLS=1` is a separate default-off experiment alongside CPU
small copies. Physical NVN pool registration supplies flags with its metadata;
the other backends use a weak wrapper preserving the previous add/set-flags
sequence. Only known CPU-uncached whole pools below 64 KiB that selected the
configured small-pool copied path can remain metadata-only. Sparse virtual
mappings, other pool kinds and actual AHB import failures remain eager.
Candidate registration shares backend submission ownership, so no worker can
publish a new lazy pool after a submission's preparation pass. Every real
submission materializes all live lazy pools before replay, releases the pool
lock, then retains the original completion wait and complete initial snapshot.
Direct UBO/SSBO access therefore still sees valid buffers. CPU-only retirement
keeps dirty/alias bookkeeping but skips Vulkan destruction and fence waits.
`DM_VK_POOL_PROF=1` counts registrations, allocations, materialization and
metadata-only retirements. NVN timing summaries include an absolute host
monotonic timestamp for precise same-checkpoint comparisons.

`DM_VK_PASS_CENSUS=1` observes pass closures without changing rendering commands.
The Android replay records closure reasons, zero/one/multiple draws, barrier mask
counts, render-target comparison results and actual LRZ transfer categories.
A short mutex protects counter updates/snapshots; bounded logs are emitted after
releasing it every 600 presents. These counts identify candidates for a later
barrier change and are not permission to remove synchronization or LRZ handling.

`DM_VK_GPU_SEGMENTS=1` creates a separate timestamp pool at startup, without
sampling until `DM_VK_GPU_SAMPLES=N` requests up to eight frames. A request skips
the partly replayed current frame, captures every submission of selected frames
30 presents apart, then stops; a hard 64-submission limit explicitly marks a
truncated frame. Each submission can record 4,096 exclusive intervals across up
to 32 main command-buffer parts. Bottom-of-pipe markers bracket render passes
(including begin/end load/store work), LRZ reads/writebacks, standalone global
barriers and compute work including its barriers. Nested barriers belong to the
outer LRZ/compute interval. Upload-command-buffer barriers are counted separately
and are not attributed to main-buffer intervals. These are completion intervals,
not utilization or isolated ALU costs; timestamps themselves can disturb binning.
Part begin/end markers expose elapsed gaps between early-submitted parts without
assuming those gaps are CPU stalls. Unclassified time remains explicit.

Only actually written queries are read, without `WAIT_BIT`, after the existing
final fence and before slot reuse; refused submissions discard the capture.
Private metadata/results survive slot reuse. Summary logs and `gpu_segments.tsv`
are emitted by the completion worker after publishing game/slot completion.
Missing endpoints, unavailable queries, ambiguous counter wraps, overlapping
intervals and exhausted capacities are reported instead of silently attributed.
Sampling off adds no GPU timestamp/reset commands, barriers or waits. Compare
sampled frames with nearby unsampled controls before treating the breakdown as a
normal frame cost. Tests execute the production planner, reducer and query hooks.

Vulkan replay treats `OP_BARRIER` with an empty bit mask as a no-op, matching
the Metal replay: it requests no ordering or cache invalidation. The recorder
carries only that mask and padding. It must preserve an active or pending-clear
pass, bound state and deferred updates. Nonzero masks retain the full pass-end
and global-barrier path, including unknown bits.
`DM_VK_SKIP_EMPTY_BARRIER=0` restores the old behavior for live comparison;
census still records empty calls but counts no actual closure when skipped.
PJD110 stock-driver DQB2, docked 1080p, same-process dialogue A/B/A:
empty-mask handling off/on/off gave 54.284/33.334/55.232 ms per frame
(18.42/30.00/18.11 FPS). The clean on window retained 329,400 empty calls
over 600 frames with zero closures; total passes fell from 534 to 154.59 per
frame, with draws/dispatches preserved. GPU submission span fell from 45.17
to 27.03 ms; these timestamps are not occupancy or clock-frequency counters.
This validates the local semantic fix, not a claim of full device utilization.

`DM_VK_DEDUP_ADJ_BARRIER=1` is an opt-in experiment for literal adjacent
nonzero barrier records in one replay block and one command buffer. The first
full barrier and all pass boundaries remain; only a following identical-scope
full barrier with no intervening record/GPU work may be omitted. Zero masks,
other records (including calls/jumps), block boundaries and command-buffer changes
break adjacency. Pass census reports candidates and actual omissions separately.
It does not establish that other nonzero barriers are redundant.

`DM_VK_TEXTURE_BARRIER` is a default-off, per-submission experiment for exact
`0x10` texture invalidation: 0 keeps the original path, 1 observes metadata while
retaining all original rendering commands, and 2 defers the pass end/full barrier.
It requires an active, drawn pass whose previous draws have no potential storage,
transform-feedback, raster-discard or unknown writes. Only direct sampled-texture
bindings and known uniform resources are initially supported. All other masks,
mixed masks, pending clears and unknown sources keep the original path.

A pending dependency snapshots all attachment storage footprints and persists
across every later draw, state change, call/jump and descriptor memo hit. Metadata
preflight uses the same versioned texture registrations without creating views or
recording uploads. Pool-relative aliases and overlapping CPU address ranges both
count; whole footprints conservatively include all mip/layer views. Virtual,
sparse, linear, fresh, dirty, unregistered, mismatched or mutually aliased sources
are rejected. Uniform checks include descriptor alignment prefixes. Vertex reads
initially reject the whole Vulkan backing buffer, covering indexed fetches beyond
the NVN bound; indirect and unresolved resources fall back. Deferred handle reads,
copies, uniform updates, clears, counters, transform feedback, dispatches and
unknown records flush before execution. Natural pass ends and the 128-draw cap
also discharge pending synchronization. No draw or shader work is dropped.

Registration/view-drop generation publication is atomic. A descriptor cache stores
the generation taken before lookup, so a racing rewrite cannot mark an older
view current. The guard checks texture/pool/dirty/upload generations before reads
and again after actual descriptor collection; a change ends/synchronizes the pass
and retries preparation before counting or emitting the draw. Observational mode
may end a hypothetical window sooner at an actual `SetRenderTargets`; its candidate
counts are not a proof that an entire interval can be merged. Cumulative reports
separate candidates, actual deferrals and fallback reasons. Device correctness and
same-scene performance comparisons are required before enabling a profile default.
Guarded mode conservatively re-emits binding and dynamic state for every draw;
pipeline and descriptor object caches remain active. This retains the command
path used for device validation after intermittent missing menu glyphs; the
precise cause of that transient remains unconfirmed. Legacy/observational modes
retain their state suppression. Adjacent barriers with no active physical pass
must not clear an observational window before a later dependent draw.

On PJD110/stock Adreno 750, the docked outdoor menu was compared off/on/off in one
process at the same 1920x1080 resolution, with complete state rebinding in all
three phases. Checkpoint windows measured 18.96/30.00/17.30 FPS. Separate one-frame
structural samples had 346/52/346 passes, with 1,024 draws and two dispatches in
each. The window CPU replay means were 21.36/8.87/22.51 ms. Screenshots retained
the menu text in all phases. These results justify this profile's opt-in default;
they do not establish correctness through sustained game progression or an FPS
floor in other scenes. Raw logs/screenshots remain in the ignored game folder.

Compute prewarm keeps the base-shader path and optionally warms exact integer-view
variants observed in successful real dispatches (`DM_VK_COMPUTE_WARM_SEEN=1`,
startup, default off). A bounded 256-entry list stores {shader, unsigned mask,
signed mask} in `vk_compute_pipelines.bin` (CMW1/version 1, fixed little-endian
header and 24-byte records). Invalid files, unknown compute shaders, overlapping
masks and non-variantable bindings are ignored. Replay records metadata only;
the existing background/drain pipeline-cache save path persists a short snapshot
with serialized atomic file replacement and retry after errors. The background
warm thread compiles exact keys after base prewarm, outside map locks; failed
prewarm does not publish a failure sentinel, so a required dispatch keeps its
original synchronous fallback. No compute work is skipped for asynchronous
readiness. Creation longer than 50 ms records its shader/masks/time even with
slow-replay profiling off. First-ever unseen variants may still compile on use.

The NVN timing wrapper is a development cost, not rendering semantics.
`DM_NVN_PROF=0` now disables it at startup or through a development env command.
Targets are snapshotted after registration and remain immutable; live changes
publish atomic slot pointers, preserving the 16-byte table / byte-8 target ABI
and in-flight wrapper calls. A live choice wins over later proc lookups.
The optional `DM_NVN_SEQ` request and `DM_SLEEP_BT` range are initialized once;
development env notifications publish updated configuration. Disabled wait/trace
paths do not scan the environment. SyncWait retains its query/result semantics
but reads elapsed diagnostic time only while tracing is enabled. Startup absence
keeps normal execution free of full NVN timing wrappers.

Vulkan zero-timeout completion queries use acquire reads of the published game
or slot-ready watermark. They take no condition mutex, read no wall clock and
never enter a condition wait. Positive waits retain their existing deadline
semantics. `DM_VK_POLL_FAST=0` restores the old expired-wait path only for a
controlled comparison. Query reports separate zero/positive calls and actual
condition-wait costs; less waiting is not by itself proof of faster frames.
Development DM_CTL env commands notify weak NVN, thread-debug and backend hooks
after setenv; the Android backend atomically publishes completion-test flags. Each retirement
snapshots the early-completion mode, so switching during reset cannot suppress
completion. Release apps still unset DM_CTL and accept no remote key input.

Vulkan host completion has two ordered watermarks: game-visible completion
requires GPU execution, copied-pool writeback, query reads and event/counter
writes; slot readiness additionally requires command-buffer reset. Submission
slots always wait for readiness before reuse, including the no-prereset path.
The opt-in `DM_VK_EARLY_COMPLETE=1` publishes game completion before reset so
CPU game work may overlap that bookkeeping; default publication remains after
reset. Host drain waits for both. The sync profile reports slot reuse waits
separately. This preserves six-slot lifetime and query ownership; local ordering
tests do not establish a physical-device improvement.

`DM_ADPF_LONG_WORK=1` optionally extends performance reporting to completed
synchronous-replay work cycles of at least 250 ms, which ordinary frame reporting
excludes. It measures the hint session threads' scheduler CPU clocks, reports
no unmeasured GPU duration, and skips unsupported or incomplete measurements.
A low-frequency observer can refresh worker membership during an open long
cycle and attempt one CPU workload-increase notification per episode; completed
cycles carry ongoing duration reports. A frontend activity epoch rejects work
crossing a pause, menu, keyboard or focus change; headless and deterministic
clock runs are excluded. Async NVN replay is excluded because acquire and
present do not delimit the same work cycle there. This is off by default and
makes no claim of overriding a platform frequency limit.

Android CPU performance requests are handled by `android/perf_android.c`.
`DM_ADPF_WORKERS=1` opts into wall-time-based busy-worker enrollment (at the next
present after 0.5 s, above 5% of a CPU), retaining the existing 300-present / 15%
policy by default. `DM_PIN_GAME=1` also enables this scan and explicitly places
the two busiest threads using CPU capacity scaled by the current frequency cap
(or current capped frequency when capacity metadata is incomplete). With one
fastest core, the second thread uses the next capacity group; with several,
both can use that group. The scanner restores the original affinity of workers
that leave the selected pair. Both switches are off by default, request no
system-wide power change, and do not bypass thermal limits. Missing metadata or
denied affinity requests preserve the system's normal scheduling. The approach
is informed by [the source project's CPU-placement reports](https://github.com/shirai91/nx2android/issues/11).

Subgroup instructions inside helper functions are inlined with the NDK's `spirv-opt`
before shader reflection and packaging (`dm/android/tools/spirv_portable.py`). Adreno 750
crashes while compiling an otherwise valid subgroup shuffle in a called function;
a synthetic shader reproduces it. Ordinary helpers and subgroup operations already in
entry points keep their original bytes. This changes no bindings or computation.

## Saves

The app keeps the game's save in its internal storage (`$DM_SAVE`, and `<DM_SAVE>_device` for a game that mounts a device save too: `hle_fs.c`), which a reinstall keeps, an uninstall deletes, and adb cannot read in a release build (it is not debuggable). The save manager (`dm/android/saves_android.c`) copies it in and out through the app's files folder, which adb, porter and the PC reach without a permission:

- `saves/<YYYYMMDD-HHMMSS>/`: one export, the save's files byte for byte, as a console's save tools copy them (so a console's save folder imports as it is, and an export goes back to a console the same way); `saves/<name>.device/` beside it holds the device save.
- **Export save** (the pause menu's Game tab) copies the committed save (never `.work`: a transaction in flight is not a save) on a thread of its own, through a hidden `.part` folder renamed when whole, and starts again if the game commits meanwhile.
- **Import save** opens a picker of the folders in `saves/`, newest first. The import is applied at the next start, before the host mounts anything (`ANativeActivity_onCreate` → `dm_saves_start`), so it never meets a commit: the menu writes `saves/import.txt` and the app ends. At the start the save it replaces is exported first (`<stamp>-before-import`), the folder is copied to `<DM_SAVE>.import` and swapped in with one `renameat2(RENAME_EXCHANGE)`.
- `porter saves` (the GUI's **Saves** tab) does the same from the PC: `apps`, `list`, `export [dest] [--name …]` (a fresh export: the app is stopped and started with `saves/export.txt`, exports and ends without starting the game, then the folder is pulled), `import <folder or .zip>` (pushed under a hidden name, renamed, named in `saves/import.txt`, and the app started to apply it). Each request carries a token the app writes back in `saves/result.txt` with its outcome.
- The files are not changed. A save made on a console belongs to that console's user; a game that keeps its user's id inside its own files (Animal Crossing: New Horizons, issue #16) reads it as another user's, since the host's one user (`hle_account.c`) is not mapped into it.

Shaders captured on the device: a game can set shaders whose code is in no game file (Xenoblade Chronicles 3, hundreds: effects and model materials), which the split cannot find. When a draw needs a shader the bundle lacks, the app saves it to `captured_shaders/<key>.bin` in its files folder (`gfx_vk_shader.c` `vk_shader_missing`; the draw is skipped this time). A port with `--install` first pulls that folder into `<build folder>/android/captured_shaders/`, which is kept from port to port, and `shader_vk.py --capture` translates it into the bundle. These shaders are not in the profile's tables: the tables stay what the game files give. So such a game draws everything only after it has been played that far once and ported again.

The install starts the app once before pushing anything: Android makes the app's files folder, owned by the app with the app's group, when the app first asks for it, and a folder the shell makes first lacks that group underneath FUSE, so the app cannot read what is pushed below it. Files whose path passes Windows' 260 characters are pushed through short hard links (adb.exe is not long-path aware). A file already on the device at its size is skipped; the port's own outputs (everything but `RomFS/` and `aoc/`, which change only with the game's version) are also compared by MD5, because a rewriter cut changes a module without changing its size.

What the port refuses: a game whose `main` renders with Vulkan or OpenGL (the Android host replays NVN only so far), and one whose shaders need an unavailable Mac-host decoding step (Unreal / Oodle). Runtime GLSLC capture is supported on Apple Silicon, or reused when already complete.

**Versions.** The newest version in the folder is packed. A version the profile was not brought up on is packed from a derived profile (upstream's `derive_profile`, in `profile-derived/`), without that version's per-build fixes. When another build is packed (GitHub issue #26):
- a profile that declares virtual address memory (a `sys_resource` row, not 0) gets 8 GB more `mem_alias` and `mem_reserve` in its derived copy (`pipeline.alias_headroom`): the address regions such a game reserves depend on its build (Donkey Kong Country Returns HD's base game reached +7.0 GB of alias region, where its tested update stays under +2.75 GB), the tested build's high-water mark does not bind another one, and the heap and the device's memory stay as they are;
- a module whose build has no registered patch, where the tested build of it has some (`dm/tools/sdk_patches.py`, the profile's `patches.py`), gets a `[RED]` line that names the patches it goes without (`pipeline.lost_patches`).

`--alias-headroom <GB>` (0 to 48; the GUI's **Extra address space**, Auto when not given) sets that headroom for any port of such a game: the derived copy, or for a version the profile was brought up on a copy in `profile-mem/` (without `patches.py`, which stays in `dm/games`), which every tool takes first. `0` keeps the profile's layout. It is for a game whose log shows `AllocateAddressRegion … refused (0x1803)` before it crashes; a game without virtual address memory keeps its layout whatever the value.

**Experimental ports** (`--experimental`, the GUI's Experimental box): a game without an Android profile. With no profile at all, upstream's survey (`<game folder>/<title ID>_survey/survey.md`) guesses a provisional one; with only an iOS profile, that profile is copied. Either way it goes to `<title ID>_build/profile/<title ID>/` with an `android.tsv` of status `experimental`, and every tool finds it there (`DM_GAMES_DIR`). That folder is where a bring-up starts; a game that works gets its profile into `nxnative/dm/games/`.

`--package` installs a port under another package than the profile's, beside the player's other build of the game (a test).

**versionCode.** The APK's versionCode is the packed Switch version number + 1 (v196608 → 196609), so a port of a game update installs over the base game's port. Android installs an APK over one with the same versionCode, but never over a higher one (`INSTALL_FAILED_VERSION_DOWNGRADE`); the only other way past that is an uninstall, which deletes the saves. `--vercode-offset N` (or `NX2A_VERCODE_OFFSET`) adds N, 0 to 65535, so a rebuild of the same version installs over an earlier rebuild with an offset; 65535 at most keeps it below the next version's port, as Switch versions are 65536 apart. A refused downgrade names the installed versionCode.

**Touch games** (`--touch`, the GUI's Touch game box). On Android the game's touch screen takes every touch in both modes, for every game (`hle_hid.c` `touch_on`), but the on-screen gamepad's controls take the touches that go down on them or near them (`front_android.c` `ctl_at`; about a quarter of a tablet's screen, at its sides), and the gamepad is shown by default. `--touch` writes `overlay=0` into the data pack's `settings.txt` over the profile's settings (`pipeline.TOUCH_SETTINGS`), as Unpacking's profile does: the gamepad starts hidden, only the menu button takes touches, and the pause menu shows the gamepad again. It is the first launch's default: the installer keeps a `settings.txt` the app already has. It costs nothing at run time (the host's touch reads are the same with the gamepad shown or hidden). A game that ignores touch while docked needs handheld mode too (the pause menu's mode item).

**60 fps** (`--fps60`). A Switch game capped at 30 needs per-build knowledge to run at 60: which memory holds its frame limit, or which code counts frames. A profile that has it (`fps_target`: the rewriter's frame-step stubs or `hle_fpslock.c`'s rows) gets `DM_FPS_TARGET=60` in `env.txt`. Otherwise the port fetches the community's config for the packed `main` build from masagrator's FPSLocker-Warehouse (`porter/fpslocker.py`; GitHub, `SaltySD/plugins/FPSLocker/patches/<title ID>/<build ID>.yaml`) and converts it: the `ALL_FPS` memory writes (pointer chains from `main`, compares; the expressions evaluated for 30 and 60) become `fpslock.tsv` in the data pack, which `hle_fpslock.c` writes on every present (`DM_FPS_LOCKS`); `MASTER_WRITE` bytes become cuts for the rewriter (`patch_nso.py` `DM_PATCHES_EXTRA`, original bytes from the game's `main`); presents follow the display (`DM_PRESENT_INTERVAL=display`), as FPSLocker paces them itself. A config using what the host lacks (`asm_a64`, `DECLARATIONS`, non-`MAIN` regions, `refresh_rate`) is refused whole, and the game keeps its own frame rate; 1,160 of the 1,462 configs convert (2026-10-28). The warehouse has no license, so its configs are fetched per port and never committed. Whether 60 holds on a device, and whether the config fixes every speed issue, is the config's and the device's: it is the player's choice.

Events: with `--progress json`, every line on stdout is one JSON object, the protocol of upstream's NSP script: `stage`, `step`, `progress`, `stage_end`, `say`; `porter` adds `result` (the outputs) at the end. A line starting `[RED] ` in a `say` is an error or warning.

## What the player installs

The player gets the bundle (`dist/nx2android-<version>-<os>-<cpu>.zip` from `python packaging/build_bundle.py`, for Windows and macOS): unzip, start `nx2android.exe` (`nx2android` on a Mac), nothing to install with pip. It does not ship toolchains; the Setup tab (`nx2android.exe -m porter doctor`, or `python -m porter doctor` from the repository) checks them and the free disk space, and its **Download missing tools** button (`porter tools --download`, `porter/fetch.py`) fetches the missing NDK, .NET SDK and platform-tools from Google's SDK repository and Microsoft's release list, checks each archive against the checksum its list gives, and unpacks them into the player's nx2android folder (`toolchains/`), which the finders search:
- **Android NDK r27c** (`ANDROID_NDK_HOME`, the configured path, or the usual install folders). No Android SDK or JDK: `mkapk.py` writes and signs the APK itself.
- **.NET SDK 10**: builds `nx_extract` and the shader translator, and runs them.
- From the repository instead of the bundle: **Python 3.11+** with `requirements.txt` (`lz4`, `capstone`, `pillow`, `fonttools`, and `PySide6` for the GUI): the port runs the engine's own Python tools (the rewriter, the shader split). The bundle carries that Python.
- **adb** (platform-tools), only to install from the tool.
- Their own **prod.keys**. Keys and game files are never copied into the repository or the app.

The player's settings, APK signing key and built translator live in their nx2android folder: `%APPDATA%\nx2android` on Windows, `~/Library/Application Support/nx2android` on a Mac, `~/.config/nx2android` elsewhere (`NX2A_HOME` overrides it). An app keeps the same signer across ports, so updates install over it.

## Adding a game

1. `python -m porter port <folder> --experimental --install`: the survey, a provisional profile and a first try on the device. Bring it up from there with the upstream tools and `devtools/` (docs in `nxnative/docs/agents`): the profile moves to `dm/games/<title ID>/`, fixes go into the core as general rules.
2. Add `android.tsv` with `status` and `tested`.
3. `python -m porter port` on its folder, install, play. Raise `status` to `playable` when it is.

`DM_VK_REBIND_FAST=1` is an opt-in CPU-only experiment: full-rebind mode still
returns fresh at every binding site and emits all original Vulkan state commands,
but clears the state cache only on command-buffer changes or explicit stale state.
Sparse GPU segment captures also record five monotonic CPU timestamps per part
(begin, recording end, command-buffer end, submit begin/end). CPU and GPU clocks
are separate: compare intervals within each domain, never subtract their epochs.
Zero/missing CPU stages are reported as missing, not inferred as no cost.

PJD110 follow-up at unchanged image quality: a same-process rebind-fast
control/on/control trial had CPU replay means 7.37/7.17/7.07 ms; the continuing
control improvement prevents attributing a benefit. Two heavy fragment SPIR-V
modules validated after offline optimization (~38% fewer static instructions),
but replacement/control/replacement GPU spans were 25.58/25.28/25.22 ms. Both
modules loaded; no stable device benefit was established. Neither experiment is
enabled by default. These windows used another stationary outdoor-menu view.

CPU part milestones also bound application queue lead: the final part's submit
returned at least 1.63-3.79 ms before the previous part could have finished on the
GPU, yet the next-part gap was 3.13-4.12 ms. The first GPU timestamp cannot precede
the first submit call; comparing elapsed intervals within each clock domain gives
this conservative bound without subtracting CPU/GPU epochs. This rules out late
application submission for those sampled final boundaries, but does not separate
upload work, GPU dependencies, timestamp perturbation or driver scheduling. It is
not proof of recoverable idle time. A startup two-stage replay trial changed view
and draw count, so its timings are not a valid effect estimate.

`DM_VK_STAGING_CACHE=1` (startup, default off) reuses exact-size copied staging
allocations below 64 KiB with known CPU_UNCACHED flags. Eight slots retain at most
1 MiB of allocation memory; oversized requirements, imported/AHardwareBuffer,
unknown/non-staging and metadata-only pools keep their original lifetime path.
Retirement goes through the existing deferred-free slot. Outside a submission,
the cache waits for full completion/post/reset retirement rather than only the
hardware fence. No allocation enters the cache before that point. A reused pool
gets a new serial and resets synchronized/dirty-span state, so the first submission
copies its whole new guest range. Buffer/image copies and QueueFinish remain GPU
operations with their original ordering. Loading before this trial still made
2,676 copied staging allocations despite lazy pools. PJD110 observed seven new
allocations and 2,669 reuses, with no cache overflow. The user requested retaining
this measured resource reduction without requiring a startup-time gain; the DQB2
profile now opts in. The cache does not defer or skip texture writes. Host tests
cover retirement and full resynchronization; startup reached the normal menu.
No loading-time improvement is claimed.

The Vulkan pool address index now uses binary insertion on registration and
remaps/removes one index on dense-array deletion, under the same pool write lock.
No full index reconstruction/qsort is needed (35,005 registrations plus 34,995
retirements in the loading workload). Equal-start entries retain relative order;
range-overlap fallback and pool-generation invalidation remain unchanged. Host
checks compare actual indexed lookups against a linear coverage oracle through
capacity, duplicate/nested ranges and randomized dense removals.

Standalone buffer-to-texture submissions may prepare a fresh ordinary destination
in the main command buffer immediately before its copy, rather than recording a
layout-only upload command buffer. Admission accepts exactly one direct upload,
optional preceding copy-stride state and END; multiple handles/copies, calls,
jumps, unknown/mixed GPU work or malformed records keep the original path. This
restriction matters: a later packaged upload in a mixed batch executes in the
upload command buffer before the main buffer. Packaged/CPU-written/linear
preparation remains unchanged, as do image-to-buffer reads and every actual copy.
`DM_VK_UPLOAD_PROF=1` reports executed transfers and new-image preparations moved
to main every 256 transfers; recorded NVN API calls are not treated as executed
GPU submissions. The decision to retain these changes uses work/resource removal
and correctness checks, per user preference, without an FPS/loading-time gate.


Texture images also have an intrusive per-pool index, protected by the existing
image mutex. A keyed image and its normalized storage key/list links share one
allocation; the storage hash still resolves identical descriptions to the same
image. Serial-only and dummy images retain their allocation/lifetime path. Pool
finalization looks up only that pool's images, with an immediate empty-pool exit;
no full storage-table traversal or restart after each hash deletion remains.
Overlap eviction and bidirectional alias discovery visit only the same pool.
Half-open storage intersection, 60-present retention, the 64-eviction bound and
8-neighbor alias bound remain; bounded selection now follows the pool list rather
than unspecified global hash-slot order. Eviction and pool finalization share
index removal, preserving dirty protection release, alias/view invalidation and
deferred GPU image/memory retirement. No image copy or synchronization is skipped.
`DM_VK_TEX_POOL_PROF=1` reports empty pool drops, retired images and actual same-pool
visits. Sanitized host checks cover empty staging pools, unrelated pools, key/hash
growth and shifts, pool address reuse, overlap/age boundaries and both retirement
routes. The criterion for retention is removed work plus correctness, without an
FPS/loading-time gate.

PJD110 startup observed 34,816 pool drops with no indexed images: these now exit
without visiting the storage table. At that checkpoint 2,837 images occupied one
texture pool, so same-pool overlap/alias traversal remains necessary and the
multi-pool filtering benefit is limited in this workload. The 116 host checks
passed, including AddressSanitizer/UndefinedBehaviorSanitizer index lifecycle
coverage. The release was installed under the original package and restarted with
the diagnostic flag removed; save graphics confirmation remains pending.


The DQB2 Android profile now sets `DM_ADAPTIVE_FPS=0` at user request, retaining
the game's original interval and normal 60 Hz pacing. A restarted stock-driver
1080p outdoor menu observed 30.00 -> 45.82 FPS over checkpoint intervals; typical
frame medians were 33.30 -> 21.40 ms and GPU submission spans 29.91 -> 19.00 ms.
The camera/companion placement differed slightly and draws increased from 1,257
to 1,382, so this is not an exact-workload A/B or causal frequency attribution.
Before/after rendering CPU replay was about 9.2-9.6 / 6.3-6.5 ms, which overlaps
GPU execution and must not be added to it. A separate bounded trace reported
about 76% app GPU activity in driver work periods; GPU MHz was not established
(no frequency transitions captured and sysfs access denied). These findings do
not establish maximum hardware performance; prior 30 ms spans were not fixed
hardware costs. No driver, global power setting or game frame-rate patch changed.
